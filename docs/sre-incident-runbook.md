# SRE Incident Runbook

Use this runbook for alerts generated by the Task API production SLO rules or synthetic checks.

## Severity

### Page

Immediate responder attention:

- sustained 5xx error ratio above 1%
- PostgreSQL or Redis readiness failure
- recovered application panic
- repeated readiness failures
- production endpoint unavailable

### Ticket

Investigate promptly but not necessarily as an emergency:

- sustained p95 latency above 500 ms
- repeated trace export failures
- monitoring/logging degradation without user-facing outage

Escalate a ticket to page severity when user impact is confirmed or the error budget is burning rapidly.

## First five minutes

1. Record incident start time and active alert.
2. Check the latest production deployment SHA.
3. Check `/health`, `/ready`, and `/version`.
4. Review the Task API Grafana dashboard.
5. Check pod rollout/status, restarts, and resource pressure.
6. Check PostgreSQL and Redis readiness/connection metrics.
7. Correlate JSON logs with `request_id`, `trace_id`, and `span_id`.
8. Inspect Tempo traces for affected routes.
9. Determine whether impact began immediately after a deployment or infrastructure change.

Useful Kubernetes commands:

```bash
kubectl -n task-manager get deployment,pods,service,ingress,hpa,pdb
kubectl -n task-manager describe deployment task-api
kubectl -n task-manager logs deployment/task-api --since=30m
kubectl -n task-manager get events --sort-by=.lastTimestamp
kubectl -n task-manager get servicemonitor task-api
kubectl -n task-manager get prometheusrule task-api-slo
kubectl get clusterissuer letsencrypt-prod
```

## High error rate

Check:

- routes contributing most 5xx responses
- recent release SHA
- panic metric/logs
- PostgreSQL connectivity
- Redis connectivity
- upstream ingress errors
- exhausted DB connections
- recent schema migration

If the error began immediately after the latest application deployment and cannot be mitigated quickly, rollback to the previous signed immutable image digest.

Do not skip database compatibility analysis before rollback when the release included a migration.

## High latency

Check:

- p95 by route
- in-flight requests
- DB wait count/duration
- PostgreSQL connection saturation
- Redis pool timeouts
- CPU/memory and HPA state
- pod scheduling/resource throttling
- slow traces in Tempo

Prefer capacity or dependency remediation when application correctness is unaffected. Roll back only when evidence points to the release.

## Dependency not ready

### PostgreSQL

Check managed database availability, connections, storage, failover state, and networking.

```bash
kubectl -n task-manager logs deployment/task-api --since=15m | grep -i postgres
```

If a recent migration caused the problem, stop further rollout and follow the database recovery procedure.

### Redis

Check managed cache availability, network path, TLS/auth settings, and pool timeout metrics.

With `RATE_LIMIT_FAIL_OPEN=true`, auth traffic can continue after an already-running API loses Redis, but readiness will intentionally fail so new traffic is not routed to the unhealthy pod.

## Panic detected

Use the structured `http_panic` log entry.

Capture:

- request ID
- trace ID
- route
- deployment commit
- stack trace

Do not paste secrets or tokens into incident channels.

If the panic is reproducible and release-specific, roll back the application and open a defect with the smallest reproducible request shape.

## Trace export failure

Confirm user-facing metrics first. Trace loss by itself is observability degradation rather than application outage.

Check:

```bash
kubectl -n monitoring get pods
kubectl -n monitoring get service otel-collector
kubectl -n monitoring logs deployment/otel-collector --since=30m
```

Then check Tempo health/storage.

Do not restart healthy application pods solely to recover tracing unless the exporter itself is stuck and other mitigations failed.

## Synthetic failure

From a separate network path, check the public URL:

```bash
curl -fsS https://YOUR_HOST/health
curl -fsS https://YOUR_HOST/ready
curl -fsS https://YOUR_HOST/version
```

If in-cluster readiness is healthy but public synthetic checks fail, investigate DNS, certificate, ingress, load balancer, WAF, and external routing before the application.

## Rollback

Application rollback should use a previously signed immutable digest.

Confirm the target version is database-compatible.

Typical workflow:

1. identify previous known-good image digest
2. verify its Cosign signature
3. update Deployment image to that digest
4. wait for rollout
5. verify health/readiness/version
6. monitor error rate and latency

Do not use mutable `latest` as a rollback target.

## Backup/restore incident

If data recovery is required:

1. stop writes or isolate affected traffic when necessary
2. determine recovery point objective
3. prefer managed provider PITR/snapshot restore for production recovery
4. restore to a new database first
5. validate schema/migrations and application checks
6. switch traffic only after validation
7. preserve the damaged database for investigation unless policy requires otherwise

The scheduled logical restore drill proves application-level dump recoverability but is not a substitute for managed snapshot recovery testing.

## Incident closure

Before closing:

- user-facing service is stable
- alerts cleared for a meaningful observation window
- current deployment SHA is recorded
- data integrity is checked when relevant
- temporary mitigations are documented
- follow-up owners and deadlines are assigned
- error-budget impact is recorded
- post-incident review is scheduled for material incidents
