# Terraform Delivery and Environment Promotion

Phase 16.1 separates Terraform planning from production apply and adds an auditable promotion path.

## Delivery flow

```text
Pull request
  |
  +-- terraform fmt / validate
  +-- optional remote plan using terraform-plan Environment
  |
  v
Merge to main
  |
  v
Manual Terraform Delivery: plan
  |
  +-- OIDC cloud authentication
  +-- remote backend
  +-- exact provider lock file
  +-- destroy/replacement guard
  +-- encrypted binary plan artifact
  +-- plan metadata + SHA-256 integrity
  |
  v
Review plan
  |
  v
Manual Terraform Delivery: apply
  |
  +-- terraform-production Environment approval
  +-- OIDC cloud authentication
  +-- verify source workflow run
  +-- verify commit == current main
  +-- download encrypted plan
  +-- verify plan and provider-lock hashes
  +-- second destroy confirmation when required
  |
  v
Apply the exact reviewed binary plan
```

The apply job never creates a fresh plan. It applies the exact encrypted plan generated by the reviewed manual plan run.

## Remote-state bootstrap

State backends are bootstrapped separately under:

```text
infra/terraform/bootstrap/aws
infra/terraform/bootstrap/azure
infra/terraform/bootstrap/gcp
```

The production cloud stacks now declare their remote backend type:

```text
AWS    -> s3
Azure  -> azurerm
GCP    -> gcs
```

Bootstrap state is intentionally separate because Terraform cannot create the backend that stores its own initial state in the same initialization step.

### AWS

Example:

```bash
cd infra/terraform/bootstrap/aws
terraform init
terraform apply \
  -var='state_bucket_name=YOUR_GLOBALLY_UNIQUE_BUCKET'
```

The bootstrap stack enables versioning, encryption, public-access blocking, TLS-only access, and `prevent_destroy`.

Example production backend config:

```hcl
bucket       = "YOUR_GLOBALLY_UNIQUE_BUCKET"
key          = "production/terraform.tfstate"
region       = "ap-southeast-3"
encrypt      = true
use_lockfile = true
```

### Azure

Example:

```bash
cd infra/terraform/bootstrap/azure
terraform init
terraform apply \
  -var='storage_account_name=YOURUNIQUESTATEACCOUNT' \
  -var='allowed_ip_ranges=["YOUR_TRUSTED_EGRESS_IP"]'
```

The storage account uses private containers, versioning, retention, TLS 1.2+, infrastructure encryption, no shared access keys, and `prevent_destroy`. Network rules default to deny; pass `allowed_ip_ranges` for trusted bootstrap/runner egress IPs or run from an approved private execution environment.

Example production backend config:

```hcl
resource_group_name  = "rg-task-manager-terraform-state"
storage_account_name = "YOURUNIQUESTATEACCOUNT"
container_name       = "tfstate"
key                  = "production/terraform.tfstate"
use_oidc             = true
tenant_id            = "YOUR_TENANT_ID"
subscription_id      = "YOUR_SUBSCRIPTION_ID"
```

### GCP

Example:

```bash
cd infra/terraform/bootstrap/gcp
terraform init
terraform apply \
  -var='project_id=YOUR_PROJECT_ID' \
  -var='state_bucket_name=YOUR_GLOBALLY_UNIQUE_BUCKET'
```

The GCS bucket uses uniform access, public-access prevention, versioning, and `prevent_destroy`.

Example production backend config:

```hcl
bucket = "YOUR_GLOBALLY_UNIQUE_BUCKET"
prefix = "production"
```

## GitHub repository variable

After choosing the production provider, configure this repository variable:

```text
TF_PROVIDER=aws
```

Allowed values are:

```text
aws
azure
gcp
```

This variable selects the provider for pull-request plans and the daily drift job.

If `TF_PROVIDER` is not configured, static Terraform validation still runs but remote PR planning and scheduled drift are skipped.

## terraform-plan Environment

Create a GitHub Environment named:

```text
terraform-plan
```

Set:

```text
Variable:
  TF_PLAN_ENABLED=true

Common secrets:
  TF_BACKEND_CONFIG_B64
  TF_VARS_B64
  TF_PLAN_ENCRYPTION_KEY
```

The backend config and production variable file are stored base64-encoded so multiline HCL can be materialized exactly:

```bash
base64 -w 0 backend.hcl
base64 -w 0 production.tfvars
```

On macOS:

```bash
base64 < backend.hcl | tr -d '\n'
base64 < production.tfvars | tr -d '\n'
```

Use a high-entropy random value for `TF_PLAN_ENCRYPTION_KEY`. The same value must be configured in `terraform-production` so the reviewed plan can be decrypted for apply.

### AWS plan identity

```text
Secret:
  TF_AWS_ROLE_ARN

Variable:
  TF_AWS_REGION
```

The role trust policy should allow only:

```text
repo:cyberyugun/Simple-Task-Manager-API-Golang:environment:terraform-plan
```

Give the plan role remote-state access plus read-only permissions required to refresh and plan the selected infrastructure.

### Azure plan identity

```text
Secrets:
  TF_AZURE_CLIENT_ID
  TF_AZURE_TENANT_ID
  TF_AZURE_SUBSCRIPTION_ID
```

Use a federated credential subject restricted to:

```text
repo:cyberyugun/Simple-Task-Manager-API-Golang:environment:terraform-plan
```

### GCP plan identity

```text
Secrets:
  TF_GCP_WIF_PROVIDER
  TF_GCP_SERVICE_ACCOUNT

Variable:
  TF_GCP_PROJECT_ID
```

Restrict the Workload Identity Provider/service-account binding to the repository and the `terraform-plan` environment.

## terraform-production Environment

Create another GitHub Environment named:

```text
terraform-production
```

Configure required reviewers before enabling apply.

Set:

```text
Variable:
  TF_APPLY_ENABLED=true

Common secrets:
  TF_BACKEND_CONFIG_B64
  TF_VARS_B64
  TF_PLAN_ENCRYPTION_KEY
```

The encryption key must match `terraform-plan`.

Configure provider-specific OIDC credentials using the same names as the plan Environment, but point them at a separate production apply identity.

Trust/federation should be restricted to:

```text
repo:cyberyugun/Simple-Task-Manager-API-Golang:environment:terraform-production
```

The apply identity should have only the permissions required to manage the selected Terraform stack. Do not use static cloud access keys.

## Pull-request plan

When `TF_PROVIDER` and `terraform-plan` are configured, infrastructure pull requests run a remote plan for same-repository branches.

Pull requests from forks do not receive the protected plan secrets and are skipped by the delivery workflow.

A destructive plan is blocked by default.

Static checks always continue to run through `.github/workflows/terraform.yml`.

## Manual production plan

After the infrastructure change is merged to `main`, run **Terraform Delivery** manually:

```text
operation     = plan
provider      = aws | azure | gcp
allow_destroy = false
```

A successful plan uploads an artifact named like:

```text
terraform-plan-aws-123456789
```

The uploaded artifact contains a single encrypted archive:

```text
terraform-plan.tgz.enc
```

After decryption, the archive contains:

```text
production.tfplan
metadata.json
.terraform.lock.hcl
```

The entire plan bundle is encrypted before upload. No plaintext Terraform plan, metadata, or provider-lock file is published as an Actions artifact. The metadata records the source commit, provider, workflow run ID, Terraform version, plan hash, provider-lock hash, action counts, and destructive resource addresses.

The artifact retention period is three days.

## Destructive plans

Delete or replacement actions are blocked automatically.

If a destructive infrastructure change is intentional, the reviewed manual plan must be rerun with:

```text
allow_destroy=true
```

That creates the encrypted artifact but does not apply anything.

The later production apply also requires:

```text
confirm_destroy=true
```

This two-stage confirmation makes an accidental destroy materially harder.

Provider-level and resource-level deletion protections remain effective independently of this workflow guard.

## Production apply

From the `main` branch, run **Terraform Delivery** manually:

```text
operation       = apply
provider        = SAME_PROVIDER_AS_PLAN
plan_run_id     = RUN_ID_FROM_SUCCESSFUL_MANUAL_PLAN
confirm_destroy = false
```

The workflow checks that the source plan run:

- is a successful `Terraform Delivery` workflow
- was started manually
- targets the exact current `main` commit
- uses the selected provider
- has matching binary plan and provider-lock hashes

Then GitHub Environment protection for `terraform-production` must approve the job before the exact reviewed binary plan is applied.

A stale plan from an older commit cannot be promoted.

## Drift detection

The delivery workflow runs every day at:

```text
19:30 UTC
02:30 Asia/Jakarta
```

The drift job uses `TF_PROVIDER` and the `terraform-plan` identity.

No difference:

```text
workflow success
```

Infrastructure drift detected:

```text
workflow failure
encrypted plan artifact retained for review
```

Destructive drift is also blocked by the destroy guard.

## OIDC-only authentication

Cloud authentication in the delivery workflow uses:

- AWS GitHub OIDC federation
- Azure federated credentials
- Google Workload Identity Federation

No AWS access key, Azure client secret, GCP JSON service-account key, kubeconfig credential, or other long-lived cloud credential is required by this Terraform workflow.

Backend state access must use the same short-lived OIDC identity.

## Security properties

Phase 16.1 adds these guarantees:

- remote state instead of repository state files
- state storage versioning and destroy protection
- provider-lock preservation from plan to apply
- encrypted binary plan artifacts
- SHA-256 verification before apply
- source workflow/run verification
- source commit verification
- plan/apply separation
- production Environment approval
- OIDC-only cloud authentication
- destructive-change double confirmation
- daily drift detection
- no Terraform apply on pull requests
